# Amina — Bilingual (English/Hausa) AI Chatbot

A production-ready support chatbot built on the Claude API, deployable to a
website widget, Telegram, WhatsApp, and Facebook Messenger from one shared
backend.

```
ai-chatbot/
├── backend/
│   ├── server.js          # Express app, all endpoints, core reply logic
│   ├── memory.js          # Session/context management
│   ├── knowledgeBase.js   # Retrieval layer (keyword now, vector-ready)
│   ├── systemPrompt.txt   # The system prompt (see docs/SYSTEM_PROMPT.md)
│   ├── package.json
│   └── .env.example
├── integrations/
│   ├── telegram-bot.js
│   ├── whatsapp-webhook.js
│   └── messenger-webhook.js
├── frontend/
│   └── index.html         # Standalone website widget
├── docs/
│   └── SYSTEM_PROMPT.md
├── Dockerfile
└── docker-compose.yml
```

## 1. Architecture

```
┌─────────────┐   ┌──────────────┐   ┌───────────────┐   ┌────────────┐
│   Website   │   │   Telegram   │   │    WhatsApp    │   │  Messenger │
│   Widget    │   │     Bot      │   │  (Cloud API)   │   │            │
└──────┬──────┘   └──────┬───────┘   └───────┬────────┘   └─────┬──────┘
       │ POST /api/chat  │ POST /webhooks/*  │                  │
       └─────────────────┴────────────┬──────┴──────────────────┘
                                       ▼
                          ┌──────────────────────┐
                          │   Express Backend     │
                          │  (single generateReply│
                          │   function, per-channel│
                          │   session key)         │
                          └───────────┬───────────┘
                     ┌────────────────┼────────────────┐
                     ▼                ▼                ▼
             ┌───────────────┐ ┌─────────────┐ ┌────────────────┐
             │ memory.js      │ │knowledgeBase │ │  Claude API     │
             │ (session store,│ │.js (KB /RAG) │ │ (Anthropic SDK) │
             │ Redis in prod) │ │             │ │                 │
             └───────────────┘ └─────────────┘ └────────────────┘
```

**Why one shared `generateReply()`:** every channel — website, Telegram,
WhatsApp, Messenger — calls the exact same function. This guarantees the
system prompt, safety rules, memory, and knowledge-base grounding behave
identically everywhere; only the "envelope" (webhook parsing, message
sending) differs per channel.

## 2. Features

- Automatic English ⇄ Hausa detection and reply-in-kind.
- Context-aware multi-turn conversation (rolling memory window + summary).
- Knowledge-base grounding with "I don't know" fallback instead of
  hallucination.
- Clarifying questions when a request is ambiguous.
- Structured output: numbered steps for processes, bullets for lists.
- Rate limiting to protect API cost and prevent abuse.
- Defense-in-depth input filtering plus model-level safety rules.
- One backend, four channels (Web, Telegram, WhatsApp, Messenger).
- Stateless-friendly session keys (`telegram:<chatId>`,
  `whatsapp:<phone>`, `messenger:<psid>`, browser-generated UUID for web) —
  ready to scale horizontally once memory.js is backed by Redis.

---

## 3. Memory handling strategy

| Layer | Mechanism | Purpose |
|---|---|---|
| Short-term | Last 12 turns kept verbatim per `sessionId` | Coherent multi-turn dialogue |
| Long-term (rolling) | Overflowed turns compressed into a running summary, injected as `<conversation_summary>` in the system prompt | Context survives beyond the window without unbounded token growth |
| Expiry | Sessions idle for 2 hours are purged | Bounds memory, avoids cross-user leakage |
| Storage | In-memory `Map` (dev) → Redis (prod, see comment block at bottom of `memory.js`) | Survives restarts, works across multiple server instances |

Session keys are channel-namespaced (`whatsapp:2348012345678`) so the same
person can have independent conversations on different channels, and no
channel can accidentally read another's history.

## 4. Conversation flow

1. User sends a message on any channel.
2. Channel handler extracts `(sessionId, text)` and calls `generateReply()`.
3. Safety pre-filter runs (`looksUnsafe`); if tripped, a safe refusal is
   returned immediately — no API call is made.
4. `knowledgeBase.js` does keyword retrieval; matching entries are wrapped in
   `<context>` tags and appended to the user's latest message.
5. `memory.js` supplies the rolling window + summary.
6. Claude generates a reply, grounded in the system prompt + context +
   history.
7. Reply is stored back into memory and sent to the user via the
   channel-specific `sendMessage()`.

```
User message
   │
   ▼
[Safety pre-filter] ──fail──▶ Safe refusal ──▶ send to user
   │ pass
   ▼
[KB retrieval] → <context> block (or none)
   │
   ▼
[Memory] → last N turns + summary
   │
   ▼
[Claude API call: system + summary + context + history]
   │
   ▼
Store reply in memory ──▶ send to user
```

## 5. Error handling

- **Anthropic API failure/timeout:** caught in `generateReply()`, returns a
  bilingual friendly fallback message instead of crashing or hanging the
  webhook.
- **Webhook handlers ack immediately** (`res.sendStatus(200)`) before
  processing, so Telegram/WhatsApp/Messenger never see a timeout and don't
  retry-storm your server.
- **Empty/whitespace input:** short-circuited with a clarifying prompt,
  no API call wasted.
- **Rate limit exceeded:** `express-rate-limit` returns HTTP 429 with a
  clear JSON error before hitting the model.
- **Malformed webhook payloads:** every handler uses optional chaining
  (`?.`) and early `return` — a missing field never throws an unhandled
  exception that takes down the process.

---

## 6. Safety rules

Enforced at two layers:

1. **Model-level** (`systemPrompt.txt`): no harmful/illegal content, no
   professional medical/legal/financial advice, no fabricated facts, no
   private data disclosure, crisis situations handled with empathy and a
   redirect to real help.
2. **Code-level pre-filter** (`looksUnsafe()` in `server.js`): a small
   pattern list that blocks obviously disallowed requests before they ever
   reach the API — belt-and-suspenders, not a replacement for the system
   prompt. Extend this list based on your domain and observed abuse
   patterns; keep it narrow enough that it never blocks legitimate
   questions.

## 7. Knowledge base integration

`knowledgeBase.js` ships with a tiny in-memory keyword-matched KB
(hours, password reset, refunds) as a working example. For production:

1. Replace the `KB` array with your real content (FAQs, policies, product
   docs), or load it from a CMS/database.
2. Swap `retrieve()` for real vector search:
   - Embed each KB entry once (offline) with an embeddings model.
   - Embed the incoming query live.
   - Cosine-similarity top-k lookup in Pinecone / Weaviate / Qdrant /
     pgvector.
3. Keep `buildContextBlock()`'s shape (`<context>...</context>`) — the
   system prompt already knows how to use it and how to say "I don't know"
   when nothing relevant comes back.

## 8. API integration example

```javascript
// Minimal call shape used by generateReply() in backend/server.js
const Anthropic = require("@anthropic-ai/sdk");
const anthropic = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });

const response = await anthropic.messages.create({
  model: "claude-sonnet-5",
  max_tokens: 1000,
  system: SYSTEM_PROMPT,           // from systemPrompt.txt
  messages: [
    { role: "user", content: "Ina bukatan sake saita kalmar sirri" }
  ]
});

console.log(response.content[0].text);
```

Website widget → backend call:

```javascript
fetch("https://yourdomain.com/api/chat", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ message: "Hello", sessionId })
});
```

## 9. Deployment guide

**Local:**
```bash
cd backend
cp .env.example .env   # fill in ANTHROPIC_API_KEY at minimum
npm install
npm start               # http://localhost:3000
```
Open `frontend/index.html` in a browser (update `API_URL` if not on
localhost:3000).

**Docker / production:**
```bash
cp backend/.env.example backend/.env   # fill in real keys
docker compose up --build -d
```

**Hosting options (any works with this codebase, no changes needed):**
- Render / Railway / Fly.io — easiest, auto-HTTPS, good for webhooks.
- A VPS (DigitalOcean, AWS Lightsail) behind Nginx + Certbot for TLS.
- AWS ECS / Google Cloud Run using the provided `Dockerfile` directly.

**Checklist before going live:**
- [ ] Real `ANTHROPIC_API_KEY` set, never committed to git.
- [ ] `CORS_ORIGIN` restricted to your actual website domain.
- [ ] Redis configured (`REDIS_URL`) for multi-instance memory.
- [ ] HTTPS enabled — required by Telegram, WhatsApp, and Messenger
      webhooks.
- [ ] Verify tokens (`*_VERIFY_TOKEN`) set to strong random values.
- [ ] Rate limits tuned to your expected traffic and budget.

## 10. Connecting each channel

### Website
Host `frontend/index.html` anywhere (or embed its `<script>`/markup into an
existing site) and point `API_URL` at your deployed `/api/chat` endpoint.

### Telegram
1. Talk to `@BotFather` → `/newbot` → copy the token into
   `TELEGRAM_BOT_TOKEN`.
2. Deploy the backend over HTTPS.
3. Register the webhook once:
   ```bash
   curl -F "url=https://yourdomain.com/webhooks/telegram" \
        "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setWebhook"
   ```
4. Message the bot — done.

### WhatsApp (Meta Cloud API)
1. Create a Meta App → add "WhatsApp" product → get `WHATSAPP_TOKEN` and
   `WHATSAPP_PHONE_NUMBER_ID`.
2. In the app dashboard, set webhook URL to
   `https://yourdomain.com/webhooks/whatsapp`, verify token matching
   `WHATSAPP_VERIFY_TOKEN`.
3. Subscribe the webhook to the `messages` field.
4. Message your WhatsApp test number.

### Facebook Messenger
1. In the same (or a new) Meta App, add the "Messenger" product, connect a
   Facebook Page, generate `MESSENGER_PAGE_ACCESS_TOKEN`.
2. Set webhook URL to `https://yourdomain.com/webhooks/messenger`, verify
   token matching `MESSENGER_VERIFY_TOKEN`, subscribe to `messages`.
3. Message your Page.

## 11. Extending it

- Swap the keyword KB for vector search once you have real content volume.
- Add a human-handoff path: when the model says "I don't know" or a user
  asks for a human, push the session to a support queue (email/Slack/CRM
  webhook) instead of just replying in-chat.
- Add per-channel rich replies (WhatsApp/Messenger quick-reply buttons,
  Telegram inline keyboards) — the text-only core stays the same.
